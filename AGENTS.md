# AGENTS.md

Instructions for AI coding agents working in `amigoact-mobile`. These rules override default behavior.

## Source of truth: the web frontend

`../amigoact-fe` (Next.js) is the source of truth for product behavior, screens, copy, permissions, and design. The mobile app is a native port of it, not a redesign.

- Before building a screen, read its web counterpart under `../amigoact-fe/src/app/(app)/` and the matching `../amigoact-fe/docs/<topic>.md`. Match the flow, fields, validation, empty states, and Vietnamese text.
- If web and mobile disagree, the web is right, unless the difference is forced by the platform (no hover, no URL bar, camera, push). Record such differences in `docs/web-parity.md`.
- When the web behavior changes, update the mobile app and `docs/web-parity.md` in the same effort. Do not invent features that the web does not have.
- Port pure logic (no DOM, no Next.js) from `../amigoact-fe/src/lib/` as-is, together with its tests: validation, formatting, permissions (`hasPermission`), topic names, pagination, Vietnam time conversion (`toLocalInput`, `fromLocalInput`). Keep names and behavior identical so the two stay comparable.
- The backend (`../amigoact-be`) owns the rules. Its `docs/` describe the API and error codes. API errors use `detail` as a stable code; the app translates codes to Vietnamese with the same table as the web.

## Expo has changed: do not trust your training data

Expo and React Native ship breaking changes every SDK release.

1. Read the `expo` version in `package.json` (currently SDK 58, React Native 0.88).
2. Fetch the matching docs: `https://docs.expo.dev/versions/v<major>.0.0/`. Append `.md` to any docs URL for Markdown.
3. For anything else, read `https://docs.expo.dev/llms.txt` and follow its links. Never answer from memory.
4. Uniwind docs: `https://docs.uniwind.dev/llms.txt`.

## Project structure

- Application code lives in `src/`. The `@/*` alias points to `src/*`.
- Routes live in `src/app/` (Expo Router, file based). Keep non-route code outside it: `src/components/`, `src/lib/`, `src/hooks/`.
- Route groups and paths follow the web: web `(app)/activities/[id]` becomes `src/app/activities/[id].tsx`, and an organization's pages live under `src/app/org/[slug]/`. Do not rename routes.
- `app.json`, `metro.config.js`, `biome.json`, and `tsconfig.json` stay at the repo root. `ios/` and `android/` are generated by prebuild and are gitignored.
- `src/uniwind-types.d.ts` is generated by Metro. Commit it, and do not edit it by hand.

## Package manager and commands

Bun is the package manager (`packageManager` is pinned in `package.json`). Never use npm, yarn, or pnpm, and never commit another lockfile.

```bash
bun install                      # install locked dependencies
bunx expo install <package>      # add a dependency: ALWAYS use this, it picks the SDK-compatible version
bun run start                    # start Metro (scan the QR code with Expo Go or a dev build)
bun run android                  # start and open on Android
bun run lint                     # Biome lint and check
bun run format                   # Biome format (writes files)
bun run typecheck                # tsc --noEmit
bun test                         # tests (bun:test, pure logic only)
bunx expo-doctor                 # diagnose dependency and config issues
bunx expo export --platform android --output-dir <scratchpad>   # production bundle check
```

Metro has to run (or `expo export` has to be run once) after you add a Tailwind class or a `global.css` change so that `uniwind-types.d.ts` is regenerated.

## Styling: Tailwind only (Uniwind)

- Style every element with Tailwind utility classes through `className`, using Uniwind (Tailwind 4). This matches the web rule "Tailwind only".
- Do not use `StyleSheet.create` and do not use inline `style={{ ... }}`. The only exception is a value that cannot be a class, such as an animated value, or a prop a library only accepts as a style object. Keep these rare and comment why.
- `src/global.css` holds only `@import "tailwindcss";` and `@import "uniwind";`. Do not add rules.
- Dark mode follows the system (`userInterfaceStyle: "automatic"`). Write dark styles with the normal `dark:` prefix.
- Colors that a prop needs as a string (icon `color`, `StatusBar`, navigator options) come from `src/lib/theme.ts`, which holds the exact hex of the Tailwind teal and slate shades used on the web. Do not scatter hex values elsewhere.

## Design rules

The web design rules apply, translated for a phone. Read `../amigoact-fe/AGENTS.md` (Design rules) first. If a rule gets in the way of a clearly better mobile interface, change the rule here, say why in the change, and follow the new rule. Do not work around it silently.

- The phone is the base layout, as on the web. For tablets, use `md:` classes to center content up to a readable width. Do not build a separate tablet design now.
- Flat design: no shadows (`shadow-*`, `elevation`), no gradients, no decorative effects. A floating layer (menu, dialog, toast, bottom sheet) may be separated with a border.
- Primary accent is teal (`teal-700` in light mode and `teal-400` in dark mode). Use neutral slate colors for text, borders, and surfaces. Semantic colors (green, amber, red, sky) carry meaning only, with the same shades as on the web.
- Do not nest cards inside cards. Separate sections with borders and dividers.
- Corner radius: inputs and buttons `rounded-sm` or `rounded-md`; cards, panels, images, and dialogs `rounded-lg` or `rounded-xl`; `rounded-full` for avatars and dots. Never beyond `rounded-xl`.
- Font: Be Vietnam Pro, loaded in `src/app/_layout.tsx`. Do not use Inter or the system font for text that the web shows in Be Vietnam Pro.
- Icons: use `Feather` from `@expo/vector-icons`. The web uses `react-icons/fi`, which is the same Feather set, so icon names carry over one to one (`FiHeart` is `<Feather name="heart" />`). `react-icons` itself does not work on React Native. Use icons freely, and prefer icons over words for what everyone understands. Every icon-only `Pressable` needs `accessibilityLabel` and `accessibilityRole="button"`.
- Touch targets are at least 44 by 44 points. Respect safe areas with `react-native-safe-area-context`. Handle the keyboard on forms, and keep long lists in `FlatList` (not `ScrollView` plus `map`).
- Every screen handles loading, empty, and error states, the same as the web.

## Authentication and backend access

- Details are in `docs/architecture.md`. Read it before writing any network code.
- The backend refuses every HTTP request without `X-Internal-Key`. On the web that key lives only on the Next.js server. **A mobile app is a public client: never put `INTERNAL_API_KEY` in the app, in `EXPO_PUBLIC_*` variables, in `app.json`, or in any bundled file.** Anything bundled can be extracted.
- Until the access strategy in `docs/architecture.md` is decided and implemented, do not write code that calls the backend directly. Build screens against typed fixtures behind the same data functions that will later call the API, so the swap is one file.
- Tokens are stored only in `expo-secure-store`. Never use `AsyncStorage` or any unencrypted storage for tokens, and never log them.
- Refresh tokens rotate on every use, and reusing a rotated token ends the session. Serialize refresh calls so two requests never refresh at once, and store the new token before retrying the request.
- Role and permission gates use `hasPermission(viewer, "module.action")` and `hasModule(viewer, "module")` ported from the web, never `role === "admin"`. The backend checks again.

## Realtime

- The app has one socket, held by one provider at the app root, as on the web (`../amigoact-fe/docs/realtime.md`). Do not open another `WebSocket`.
- The socket connects with a one-time ticket, never with the access token in the URL. Reconnect when the app returns to the foreground (`AppState`), and close the socket in the background.

## Language

- Code identifiers, file names, and comments are in English. Text shown to users is in Vietnamese, with the same wording as the web.
- Exception: `.md` files may be written in Vietnamese.
- Identifiers must be ASCII.
- Dates and times display in Vietnam time (`Asia/Ho_Chi_Minh`), with the same helpers as the web.

## File size limits

- Every `.ts` file is at most **350 lines**, and every `.tsx` file is at most **260 lines**, the same as the web.
- When a file approaches the limit, split it into smaller components or modules instead of adding more code to it.

## Git: never commit, branch, or push without an explicit command

- Do not run `git commit`, `git push`, `git checkout -b`, `git switch -c`, `git branch`, or `git tag`, and do not open a pull request, unless the user asks for that action in the current message.
- When the user asks to commit "per stage" in a message, commit each finished stage locally, one commit per stage, and never push. That permission lasts only for that task.
- Finishing a code change does not give you permission to commit. Summarize what changed and wait for the next instruction.
- Do not stage files with `git add` unless the user asks or a commit was asked for.
- Commit messages are in English.

## No junk files in the repository

Never create or commit these: `node_modules/`, `.expo/`, `dist/`, `ios/`, `android/`, `web-build/`, `.env` files (only `.env.example` is allowed), signing files (`*.jks`, `*.p8`, `*.p12`, `*.key`, `*.mobileprovision`), log files, `.DS_Store`, `Thumbs.db`, `*.tmp`, `*.bak`, `*.tsbuildinfo`, scratch scripts, and generated output other than `uniwind-types.d.ts`.

Put scratch work and bundle outputs in the session scratchpad directory, not in the repository.

## Documentation

- Write detailed documentation in `docs/`, one file per topic. Keep `README.md` short: setup, commands, and links to `docs/`.
- When behavior changes, update the matching file in `docs/` in the same change. Keep `docs/web-parity.md` current: it lists every web screen and its mobile status.

## Testing

- Pure logic ported from the web comes with the web's tests, run with `bun test`. Tests must not touch the network or native modules.
- Screens are checked by running the app (Expo Go or a development build) and by `bunx expo export`, which proves the bundle builds. Say plainly in your report what you ran and what you could not run.

## Quality gates

There is no CI workflow in this repo yet. Until one exists, run these locally before you report a change as done, and report the real results. If a gate fails, fix the code. Do not weaken or skip a gate. Never say CI passes without evidence.

| Gate | Check |
| ---- | ----- |
| 01 | Install with frozen lockfile (`bun install --frozen-lockfile`) |
| 02 | Lint (`bun run lint`) |
| 03 | Format check (`bunx biome format`) |
| 04 | Type check (`bun run typecheck`) |
| 05 | Bundle builds (`bunx expo export --platform android`) |
| 06 | Dependencies healthy (`bunx expo-doctor`) |
| 07 | Tests (`bun test`, once test files exist) |
| 08 | `.ts` files at most 350 lines, `.tsx` files at most 260 lines |
| 09 | Identifiers are ASCII |
| 10 | No junk files tracked, no secrets in the bundle |
